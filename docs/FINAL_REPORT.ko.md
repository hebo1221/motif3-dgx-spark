# Motif-3를 Spark 한 대에서 돌려보고, 여기서 멈추기로 했다

처음에는 3,147억 파라미터 규모의 모델을 128 GB 메모리에 넣어보고 싶었다.
혼합 IQ2 모델은 83.56 GiB에 들어갔고, 공개한 tg128 측정에서 16.49토큰/초가
나왔다. 다만 원본 BF16 대비 품질 유지 기준은 통과하지 못했다.

그다음에는 정밀도를 더 남기고 SSD에서 필요한 전문가 가중치만 읽으면 어떨지
확인했다. 약 630 GB인 원본을 무손실 압축으로 보관하고, 전체 복원 해시가
일치하는지 검증했다. 압축 데이터는 447.84 GB였다. 원본을 다시 전부 펼치지
않고 Q4_K로 변환하는 경로를 만들었고, 51개 MoE 층의 전문가를 모두 실행했다.
일반 가중치는 유지했고, 실행에 쓰는 가중치 데이터는 합계 186.90 GB였다.

**긴 실행의 결과는 생성 1,024토큰, 평균 2.81토큰/초였다.** 입력 처리까지
약 375초가 걸렸다. 목표였던 지속 3~5토큰/초에는 못 미쳤다. 답변도 토큰
한도까지 초안과 검토를 이어갔으므로, 이 속도를 완성된 답변의 처리량으로
볼 수는 없다.

## 남길 만한 것

모델 파일 하나 외에도 재사용할 수 있는 작업이 남았다.

- 공개 IQ2 모델과 고정 런타임, 토크나이저 수정 패치, 측정 기록.
- MTP 실험과 모델 없이 실행할 수 있는 수치 일관성 검사.
- 문서 에이전트의 실제 응답과, 근거를 인용하고도 틀린 사례.
- BF16 무손실 보관 형식과 복원기, 아카이브 직접 Q4 변환기, 전문가 로더.
- 캐시·읽기 방식별 결과와 GPU 없이 확인하는 공개 기록 검증기.

가장 의외였던 부분은 캐시였다. 전문가 8,192개를 보관할 때보다 128개만
보관할 때 이 실행에서는 더 빨랐다. 큰 전용 캐시와 운영체제 파일 캐시가
메모리를 중복 점유하는 것이 원인 후보였다. 실행 순서와 캐시 상태를 완전히
통제한 실험은 아니어서 원인을 확정하지는 않았다. 스레드를 늘리거나 읽기
방식을 바꾸는 것으로도 뚜렷한 추가 개선을 얻지 못했다.

## 품질에 대해서는 어디까지 아는가

Q4의 16문항 합성 검사는 정확한 JSON 일치 기준으로 10개를 통과했다.
실패 6개는 키·배열 구조 2개, 코드 블록 2개, 추가 필드 2개였다. 특히 추가
필드 사례는 요구한 값이 들어 있었고, 질문도 추가 키를 명시적으로 금지하지
않았다. 따라서 이 점수를 일반적인 추론 정답률이나 실사용 불합격으로
해석하면 안 된다. 기존 점수는 바꾸지 않고 채점 한계를 함께 남겼다.

**원본 BF16에는 같은 16문항 검사를 하지 않았다.** 이전의 작은 선택지 검사에서
BF16과 IQ2가 각각 3/4였지만, 고정 접두부 뒤 선택지 점수를 비교한 검사였다.
자유 답변이나 실제 업무의 합격 판정이 아니다. 이번 응답 문제가 원본에도
있는지, Q4 양자화나 런타임에서 생겼는지는 확인하지 못했다.

앞서 IQ2가 perplexity·KL 유지 기준을 놓친 것과 이번 Q4 결과는 별개다.
캐시 설정 사이의 출력 수치 일치, 원본 복원 해시 일치도 각각의 구현 검증이지
모델 품질 통과 증거가 아니다.

## 여기서 닫는 이유

돌아가는 공개 모델, 재사용할 코드, 측정한 한계가 남았다. 여기서 추가 성능을
끝없이 좇기보다 다른 사람이 이 과정을 읽고 확인할 수 있게 남기기로 했다.

새 Q4 모델 다운로드나 완성된 자율 에이전트를 내놓는 것은 아니다. Q4와
BF16의 동일 조건 품질 비교, 운영용 Q4 야간 작업 큐는 미완료로 남긴다.
추가 연구를 약속하지 않고, 재현 오류와 사실 정정만 작은 유지보수 범위로
다룬다. 원본 모델과 실험 기록은 보존한다.

[최종 실험 자료](../experiments/ssd-offload/README.md)에는 측정값, 실제 응답,
코드, 실행 환경의 가정이 있다. 모델을 받지 않고도 다음 명령으로 공개 파일
해시와 16문항 점수, 저장된 속도 요약의 일관성을 확인할 수 있다.

```sh
python3 experiments/ssd-offload/verify.py
```

이 명령은 GPU 실험을 다시 하는 것이 아니다. 공개한 기록이 서로 맞는지
확인하는 도구다.
