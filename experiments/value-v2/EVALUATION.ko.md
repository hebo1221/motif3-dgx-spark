# 평가 방법과 해석 범위

이번 작업은 기존 실패를 고치는 개발 검사, 새 확인 질문, 수치 일관성 검사를 분리했다. 어느 결과도 BF16 원본 대비 IQ2의 품질 보존 점수가 아니다.

## 문서 업무 평가

프로젝트의 실제 보고서 다섯 개를 바이트 변경 없이 복사했다. 질문과 문서별 정답 검토 기준은 실행 전에 `workflows/cases.json`에 고정했고, SHA-256을 `workflows/freeze.json`에 기록했다. 질문은 이 작업을 수행한 assistant가 작성했다. 독립 사용자의 실제 업무 30개나 블라인드 벤치마크를 확보한 것으로 보고하지 않는다.

- **개발 질문 4개:** 기본 모델 선택, BF16 시도 해석, 대상 혼동 실패, 처리량 계산. 답변과 실패를 보고 실행기만 보완했다.
- **확인 질문 8개:** 공개 문구, 토큰 일치의 의미, 과거·현재 시험 조건, 모델 비교의 한계, 서버 시작 시간, 개선 우선순위, 도구 범위, 중간 오류와 최종 정답. 최종 v3 소스가 고정된 뒤 두 모델에서 실행했다.
- **알려진 실패 관련 재검사 2개:** HELDOUT-020의 대상 혼동과 두 보고서를 종합한 답변의 끝맺음. 전자는 이미 본 같은 질문이다. 후자는 기존 짧은 발췌 문서 대신 전체 보고서를 사용하는 관련 업무다. 새로운 독립 정답률로 계산하지 않는다.

같은 프로젝트 문서와 서로 연관된 질문으로 구성되므로 이 표본에서 사용자 모집단의 성공률이나 통계적 우위를 추정하지 않는다. 확인 질문은 해당 모델 실행에서 개발용으로 재사용하지 않았으나, 질문 작성과 정답 판단은 같은 assistant가 수행했다. 질문별 기준은 사전에 고정했고, PASS/PARTIAL/FAIL 집계 방식과 설명은 답변을 본 뒤 작성했다. 독립 사전등록 연구라고 부르지 않는다.

## 실행과 정답을 구별

`answer_produced`는 도구 호출·인자·대상 범위·실제 원문 구절·표면적 끝맺음 검사를 통과했다는 뜻이다. 다음 세 층을 구분한다.

1. **실행:** 모델이 유효한 호출을 만들고 요청한 자료를 실제로 읽었는가.
2. **출처:** 선택한 행이 읽은 파일에 있고, 인용한 바이트가 원문과 같은가.
3. **내용:** 질문이 요구한 판단을 실제 원문에 맞게 했는가.

내용은 원시 답변과 원문, 고정한 `review_criteria`를 함께 읽어 assistant가 검토했다. 모델의 자기 평가나 정답 문자열 자동 포함 검사로 채점하지 않았다. 판단 기록에는 응답 파일 해시와 기준 파일 해시를 연결한다.

- **PASS:** 요구한 핵심 항목을 모두 충족하고 중요한 근거 오류가 없음.
- **PARTIAL:** 주된 설명은 맞지만 요구한 항목이나 조건이 빠짐. 중요한 오판을 승인하지 않음.
- **FAIL:** 비교 대상·부정·지표를 잘못 해석하거나 근거 없는 핵심 주장을 승인함. 실행 실패로 답변이 없는 경우도 별도로 FAIL로 기록함.

본문의 잘못된 행 번호처럼 핵심 결론과 구분할 수 있는 출처 표기 문제는 별도 주석으로 남긴다. 실제 인용이 있더라도 결론의 충분한 근거가 되지 않을 수 있다. 질문별 판정과 이유가 최종 점수보다 우선한다. 패키지의 예제 답변은 오류까지 원래 그대로 보존했다.

## 개발 실패와 수정 순서

첫 버전은 모델이 원문 구절을 직접 복사하도록 했다. Qwen 개발 질문 4개 모두에서 부호 변경이나 잘못 붙인 구절이 거절됐고, 같은 호출 반복으로 중단했다. 실패를 숨기지 않고 `qwen-development-v1`에 보존했다.

두 번째 버전은 모델이 문서 행을 고르면 프로그램이 원문을 붙이도록 바꿨다. Qwen은 4개 중 3개의 답변을 만들었으며, 하나는 8행 상한을 1행 초과해 거절됐다. 내용도 모두 맞지는 않았다. 처리량 차이 `7.36 tok/s`를 증가율로 부르고 대기시간 감소율로 써도 된다고 답한 경우를 보존했다. 같은 v2에서 Motif는 4개의 요구사항을 충족하는 답변을 냈으며, 처리량 증가율은 실제 계산 도구를 사용해 약 50.3%로 구했다.

확인용 v3는 실제 짧은 문단을 선택할 수 있도록 상한을 16행·4,000자로 조정하고 색인·보고서 출력 도구를 더했다. **확인 질문을 실행한 뒤 이 v3 소스는 수정하지 않았다.** 개발 v1/v2와 확인 v3의 점수를 합쳐서 단일 성능 점수로 발표하지 않는다.

Motif의 확인 질문 한 건은 필요한 두 문서를 읽고도 다른 자료를 계속 읽다가 8단계를 소모해 보고서를 만들지 못했다. 이 실패 이후 별도 **v4**를 만들었다. 마지막 단계의 허용 도구를 `finish_report`로 좁혀 근거에 따른 결론 또는 근거 부족을 보고하게 한다. 확인용 점수는 실패를 포함한 v3 그대로 유지한다. v4의 알려진 실패 재검사를 새로운 독립 시험으로 표시하지 않는다.

v4 경계 검사 30개가 Mac과 Spark에서 통과했다. 완료된 v3 업무 17개를 새 모델 호출 없이 재생했을 때 모든 요청·실행·보고서가 같았다. v3 실패 사례는 앞의 7개 요청이 같고 마지막 요청의 허용 도구에서만 의도한 분기가 있었다. 이 재생은 소프트웨어 변경 범위 확인이며 모델의 새 정답률이 아니다. [재생 기록](evidence/v4-recorded-replay.json)에 상세 결과가 있다.

기존 고정 100문항은 이번에 전체 재실행하지 않았다. 이전 Motif 99/100과 Qwen 100/100은 이전 버전·자료의 결과로 남는다. 대상 혼동 하나를 고쳤다는 이유로 과거 점수를 100/100으로 변경하지 않는다.

## 실행 조건과 시간

동일 GB10에서 한 모델씩 실행했다. Motif는 기존 direct IQ2 + MTP draft 1, Qwen은 Qwen3-8B Q8_0 + 기존 옵션 파서를 사용했다. 각 비교 단계의 클라이언트는 두 모델에 동일하다. greedy, thinking off, prompt cache off, 한 슬롯, context 22,016, batch 2,048 / ubatch 512 조건이다.

이는 모델·템플릿·파서·양자화 구성 전체의 비교다. Motif 원본 가중치와 양자화만 바꾼 실험이나 Qwen의 최선 성능 탐색이 아니다. 다른 prompting, thinking 모드, 모델 크기 또는 실행기로 결과가 달라질 수 있다.

질문별 시간은 서버 준비 후 검색·열람·계산·수정·답변까지다. 모델 적재는 제외한다. 같은 자료를 사용하더라도 필요한 답변 길이와 호출 수가 다르므로 토큰 생성 속도의 직접 비교로 사용하지 않는다. 파일 캐시는 통제하지 않았다. 원시 기록의 서버 준비 시간도 냉시작 우위를 주장하는 자료로 사용하지 않는다.

## 수치 검사

수치 검사는 모델이 없는 Q8_0 행렬 시험과 Qwen의 고정 토큰 재입력 시험이다. 원래 경로 → 후보 경로 → 원래 경로 복구, 실제 로딩한 라이브러리, 비교 전후 해시를 기록한다. 출력 지문이 같은 복구 제어와, 각 float를 직접 비교한 단일 실행 안의 일치 여부를 구분한다.

Q8_0 행렬 시험은 한 GPU·세 모양·세 묶음 폭이다. 작은 패치가 활성화되는 확인 범위는 그중 여섯 조합이다. 모델 내부 logits의 미세 차이를 실제 정답 오류로 세지 않으며, 같은 IQ2의 실행 일치와 BF16의 원본 품질 보존도 구분한다. 자세한 범위와 성능 비용은 [수치 검사 설명](runtime/README.ko.md)에 있다.
