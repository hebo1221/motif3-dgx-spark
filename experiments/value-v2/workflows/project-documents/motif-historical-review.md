# Motif-3 양자화 작업 검토와 다음 방향

검토일: 2026-09-05 KST  
대상 작업: `motif3 2bit 양자화 검증` — `REDACTED-TASK-ID`  
원격 작업 폴더: `/opt/motif-work/motif3-quant`

**판단**

지금 가장 가치 있는 후속 작업은 공개 모델·최종 토크나이저·MTP를 하나의 검증된 실행 조합으로 묶고, 실제 요청에서 이득을 확인하는 것이다. 기존 IQ2 형식의 비트 배분과 작은 보정 어댑터를 다시 탐색하는 일은 우선순위를 낮추는 편이 낫다.

양자화 연구를 계속한다면 먼저 고정밀 모델과의 같은 문항 비교로 실패 원인을 분리해야 한다. 지금까지의 결과는 기존 후보들을 기각하기에는 충분하지만, Motif-3의 좋은 2bit 양자화가 원천적으로 불가능하다는 증거는 아니다.

이번 검토는 초기 요청부터 9월 5일 v1.2.0 공개까지의 주요 대화, 실험 보고서, 실행 계약, 평가 요약, MTP 소스와 패치, 공개 자료를 대조했다. 저장된 MTP 원시 기록에서 토큰 배열과 집계 수치를 별도로 재계산했다. 모델 추론·학습을 새로 실행한 검증은 아니다.

**실제로 확보한 성과**

| 항목 | 확인한 결과 | 해석 범위 |
|---|---|---|
| 공개 직접 양자화 모델 | BF16 → IQ2_XXS, 89,720,474,560 bytes, 약 83.56 GiB | 전체 코어 모델 구동에 성공 |
| 공개 실행 속도 | pp512 316.71 tok/s, tg128 16.49 tok/s | 공개 런타임의 특정 짧은 엔진 벤치마크 |
| 원본 분포 보존 | 49,152-token 평가에서 BF16 대비 PPL 비율 1.411541, 평균 KLD 0.454130 | 사전에 정한 1.10 / 0.10 기준 미달 |
| 직접 양자화 모델의 작업 진단 | 한국어 212/300, 일반 149/180, raw tool 12/30, 보조 경로 tool 17/30 | 고정밀 모델과 같은 문항 비교는 미완료 |
| 최종 토크나이저 수정 | 확장 후보에서 공식 token ID 4,164,390개 일치 | 입력 토큰 정합성에 관한 성과 |
| MTP | 다른 IQ2 타깃 H0v2에서 5,120/5,120 토큰 일치, 복구 arm도 동일 | 한 GB10, 다섯 한국어 문맥 깊이, greedy 생성 |

공개 모델의 정체와 품질 한계는 [Hugging Face 모델 카드](https://huggingface.co/jhkim55/Motif-3-Direct-IQ2-XXS-DGX-Spark)에 명시되어 있다. MTP의 별도 타깃과 적용 범위는 [v1.2.0 기술 문서](https://github.com/hebo1221/motif3-dgx-spark/blob/v1.2.0/docs/MTP_EXPERIMENTAL.md)에 공개되어 있다.

한국어 총점 212/300은 초기 재양자화 모델과 같지만 세부 결과는 다르다. 직접 양자화 모델의 현재 저장 결과는 KMMLU 126/200, KoBEST 86/100이다. 오래된 125/200, 87/100을 현재 모델의 세부 점수로 가져오면 안 된다.

**1. 첫 후속 실험은 공개 모델과 MTP의 연결 검증**

현재 공개 GGUF의 SHA-256은 `9d6f7aee…80c5a`, MTP 실험 타깃은 `dff7f7db…cab9`다. 전자는 직접 BF16 양자화이고, 후자는 Q5에서 재양자화한 H0v2다. 비슷한 파일 크기가 호환성·속도·출력의 동일성을 보장하지 않는다.

런타임도 최종 조합을 다시 묶을 필요가 있다. 정식 MTP 실험의 격리 빌드는 기준 커밋 `cc3f13b3…`에 MTP 및 진단 변경을 적용한 상태다. 현재 그 소스의 변경 목록에는 최종 토크나이저 패치의 `src/llama-vocab.cpp` 변경이 없으며, 공개 토크나이저 패치가 추가로 적용 가능한 상태임을 읽기 전용으로 확인했다. 공개 문서는 패치를 함께 적용하는 절차를 제공하지만, 패치 적용 검사는 그 조합의 전체 모델 추론 증거를 대신하지 않는다.

따라서 다음 대상은 정확히 다음 조합이어야 한다.

`공개 direct-IQ2 GGUF + 최종 토크나이저 패치 + MTP 패치 + 고정한 sidecar`

짧은 로딩·출력 점검 후 같은 타깃의 MTP off/on을 비교하고, 기존 다섯 문맥 깊이와 새로운 한국어·코드·도구 프롬프트를 포함한다. 정상 EOS, 도구 호출 종료, 스트리밍, 다중 턴을 확인한다. 기존의 `ignore_eos=true`, 1,024토큰 강제 생성은 커널 진단용으로 계속 보존하되, 실제 대화 검증을 추가해야 한다.

**2. 생성 속도보다 요청 완료 시간을 다음 최적화 지표로 삼기**

MTP 원시 기록의 SHA-256이 공개 집계의 원본 해시와 일치했다. 기록 속 실제 토큰 배열, 생성 시간, draft 수락 수를 독립적으로 계산해 아래 결과를 확인했다.

| 지표 | 재계산 결과 |
|---|---:|
| Target 전 | 14.5966 tok/s |
| Target 후 | 14.5778 tok/s |
| 두 Target의 평균 | 14.5872 tok/s |
| MTP | 17.5565 tok/s |
| 생성 처리량 비율 | 1.203553배 |
| Draft 수락률 | 2,993 / 6,353 = 47.1116% |
| Target–MTP 일치 | 5,120 / 5,120 토큰 |
| Target 전–후 일치 | 5,120 / 5,120 토큰 |

추가로 기존 기록의 `request_wall_ms`를 집계했다. 서버 시작과 워밍업을 제외한 다섯 요청의 시간 합계이며, Target은 전·후 두 arm의 합계를 평균했다.

| 기존 기록의 요청 시간 | 값 |
|---|---:|
| Target 합계 평균 | 423.01초 |
| MTP 합계 | 364.42초 |
| 요청 시간 기준 속도 비율 | 1.1608배 |
| 대기시간 감소율 | 13.85% |
| 16K 입력 한 사례의 대기시간 감소율 | 8.72% |

이는 기존 다섯 강제 생성 요청을 사후 집계한 기술적 관찰이다. 실제 사용자 집단의 평균 지연이나 p95를 추정한 값은 아니다. 그래도 입력 처리 시간이 긴 요청에서는 생성 가속의 체감 이득이 줄어든다는 점을 보여준다.

다음 비교에는 세 조건이 유용하다: 기존 공개 런타임의 target-only, 통합 패치 런타임의 target-only, 같은 통합 런타임의 MTP. 이렇게 해야 런타임 변경 자체의 영향과 MTP의 추가 이득을 분리할 수 있다. 서로 다른 문맥의 16.49 tok/s와 17.56 tok/s를 직접 나눠서 개선율로 사용해서는 안 된다.

Draft 길이는 1·2·3을 작은 개발 세트에서 비교할 만하다. [Motif 공식 배포 문서](https://huggingface.co/Motif-Technologies/Motif-3)는 공식 vLLM 환경에서 1토큰 설정을 최적이라고 설명한다. GB10·IQ2·llama.cpp에서도 최적이라는 뜻은 아니지만, 현재 고정한 3을 그대로 유지하기보다 재측정할 이유는 된다. 선택 기준은 수락률보다 요청 완료 시간과 추가 메모리다.

선택한 설정만 새 프롬프트와 반복 순서 교차를 통해 확인한다. 먼저 동시성 1에서 첫 응답 시간·토큰 간 지연·완료 시간·최대 통합 메모리를 측정하고, 그 뒤 동시성 3으로 넓힌다. 성능의 실용적 판정 기준도 실행 전에 별도로 정한다.

**3. 품질 회복보다 먼저, 실패가 어디에서 생기는지 확인하기**

고정밀 teacher와의 PPL/KLD 비교는 이미 있다. 빠진 것은 한국어·도구 과제에서 BF16/Q5가 실제로 얼마나 더 잘하는지다. 어댑터끼리의 대조 실험은 이를 알려주지 못한다.

마지막 FunctionChat v26에서 control 47/100, candidate 45/100이었고, 무관 도구 거절은 각각 2/20, 1/20이었다. 하지만 CALL 도구 선택과 SLOT 대상 도구 제안은 각각 40/40이었다. 또 `삼백 초`를 숫자로 정규화한 값을 문자열에 그대로 없다는 이유로 거부하는 정책 오류도 있었다. 이런 오류를 양자화 손실 하나로 설명하면 잘못된 문제를 학습하게 된다.

전체 300문항을 바로 돌리기보다, 미사용 데이터에서 CALL·인자 누락·무관 도구·한국어 판단을 고르게 담은 30–60개 진단 문항부터 시작하는 편이 낫다. 두 비교를 구분한다.

| 비교 | 고정할 것 | 알아낼 것 |
|---|---|---|
| BF16 또는 Q5 vs direct IQ2 | 최종 체크포인트 계통, 런타임, 프롬프트 token ID, 템플릿, 생성 설정, 채점 | 정밀도 변화에 따른 작업 차이 |
| 고정 출력/정밀도에서 공식 처리 경로 vs 현재 처리 경로 | 원시 출력 또는 기준 가중치 | 템플릿·parser·구현 차이 |

원시 생성, native tool_calls, 후처리된 결과를 각각 기록한다. Q5를 쓰면 Q5-relative라는 한계를 명시한다. 공식 실행기와 llama.cpp의 연산 정합성도 작은 독립 표본으로 먼저 점검하면 같은 실행기 버그를 양쪽 비교에 공통으로 숨기는 일을 줄일 수 있다.

고정밀에서도 실패하면 원 모델·지시 형식·처리 정책 문제를 우선 본다. IQ2에서만 실패하면 그 사례의 호출 시작, 함수 선택, 인자 누락, 종료 토큰 등 구체적 경계에 맞춰 양자화 연구를 설계할 수 있다. 이 규모는 원인 진단용이며, 품질 비열등성을 통계적으로 입증하는 최종 평가 규모는 별도로 산정해야 한다.

**4. 기존 방법의 실패를 해석할 때 좁혀야 할 결론**

104 GB 후보의 같은 문항 비교 결과는 다음과 같다. 괄호는 direct IQ2 대비 정답 수 변화다.

| 후보 | 한국어 300 | 일반 180 | Raw tool 30 | 보조 경로 tool 30 | Decode 변화 |
|---|---:|---:|---:|---:|---:|
| Direct IQ2 | 212 | 149 | 12 | 17 | 기준 |
| GEMQ식 expert overlay | 211 (−1) | 148 (−1) | 8 (−4) | 13 (−4) | −18.23% |
| Block 40+52 Q8 | 211 (−1) | 150 (+1) | 9 (−3) | 13 (−4) | −11.82% |
| Terminal-KL rank 4 | 215 (+3) | 149 (0) | 8 (−4) | 11 (−6) | −5.60% |

후보를 범용 개선본으로 승격하지 않은 결정은 타당하다. 평균 KL 개선과 작업 개선이 일치하지 않았고, 한국어 +3건도 해당 평가에서 통계적 우위를 입증하지 못했다. 특히 30개 tool 진단은 큰 회귀를 발견하는 데 유용하지만 작은 개선을 안정적으로 판정하기에는 좁다.

다만 이 실험은 GEMQ 전체를 Motif에 재현한 것이 아니다. 로컬 실행 계약도 `gptq_equivalence`, `router_finetuning_equivalence`, `gemq_kernel_equivalence`를 미입증 항목으로 남겼다. [GEMQ 공식 구현](https://github.com/jndeng/GEMQ)은 전역 비트 배분뿐 아니라 GPTQ, 라우터 재학습, 양자화 실행 커널을 포함한다. 이번 실패는 구현한 할당·overlay·보정 후보에 대한 결과다.

후반의 다중 영역 KL 보정과 FunctionChat까지 살펴보면, 단순히 tool 데이터 가중치를 더 주자는 제안도 이미 시도한 방향과 겹친다. 그 재시도보다 기준 모델 비교를 먼저 하는 것이 낫다. 큰 overlay에서 관측한 속도 저하 역시 해당 저장 형식과 실행 경로의 결과이므로, 전문가별 혼합정밀도 자체가 항상 느리다는 결론으로 확대하면 안 된다.

**5. 2bit 연구를 이어갈 경우의 조건부 방향**

새로운 315B 전체 파일을 곧바로 만들기보다, 실제로 미검증인 축 하나를 작은 실험으로 확인한다.

- 지원되는 작은 MoE에서 공식 GEMQ의 GPTQ·라우터 재학습·실제 양자화 추론을 재현하거나, Motif의 제한된 블록에서 저장된 활성값을 이용해 오차와 라우팅 변화를 진단한다. 부분 블록 결과는 전체 모델의 품질 근거로 승격하지 않는다.
- 이후 Motif로 옮긴다면 generic·한국어·tool의 독립 개발 데이터에서 양자화 후 입력 분포와 라우팅 변화를 함께 측정한다. teacher 분포 평균 하나로 후보를 고르지 않는다.
- 저장 표현을 바꾸는 연구라면 [QTIP](https://github.com/Cornell-RelaxML/qtip) 같은 trellis 계열이 IQ2_XXS 배분과는 다른 후보군이다. 다만 Motif·ARM64·GB10에 적용되는 변환기와 커널 검증이 필요하며, 현재 자료만으로 성공을 예상할 근거는 부족하다.
- 정확도만 좋아지는 가짜 양자화 결과와 실제 저장·추론 결과를 먼저 일치시킨다. 실제 커널의 속도·메모리 비용을 통과한 후보만 전체 모델 작업으로 넓힌다.

최신 방법을 더 나열하는 것보다, 미검증 요소를 하나 선택하고 양성 대조군부터 만드는 편이 연구 효율이 높다. 작은 모델의 높은 정밀도 양자화가 Spark 실사용에서 더 낫다는 과거 대화의 주장도 아직 같은 작업 비교로 입증되지 않았다. 실사용 선택이 목적이라면 비교 모델 하나를 동일한 평가에 추가하는 것이 좋다.

**권고하는 순서**

1. 현재 모델·토크나이저·런타임·sidecar를 한 manifest로 묶고, 공개 GGUF에서 통합 MTP를 검증한다.
2. 실제 요청에서 draft 1·2·3 중 설정을 고른다. 정상 종료와 API 정확성을 유지하면서 요청 시간 이득을 확인한다.
3. 고정밀과 direct IQ2의 작은 같은 문항 비교로 품질 실패의 원인을 분리한다.
4. 시스템 성과는 토크나이저, Motif MTP 통합, 배치 크기에 따른 CUDA 수치 차이 재현·수정으로 나눠 기여하기 쉽게 정리한다. 같은 문제가 [llama.cpp 이슈 #25618](https://github.com/ggml-org/llama.cpp/issues/25618)에도 보고되어 있어, 다른 모델에도 통하는 작은 재현 사례를 만드는 연구 가치가 있다. 현재 수정이 그 전체 이슈를 해결했다는 뜻은 아니다.
5. 추가 양자화는 원인 진단에서 분명한 회복 가능성이 확인된 경우에만 진행한다.

이 우선순위는 성공을 보장하는 예측이 아니라, 이미 확보한 증거를 활용하면서 다음 실험이 답할 질문을 선명하게 만드는 제안이다.

**운영과 기록의 보완**

현재 조회에서 내부 저장장치 여유는 약 3.8 GiB, 외장 SSD는 약 18 GiB다. 공식 BF16 GGUF 약 629.69 GB와 direct IQ2 파일은 외장 SSD에 실제로 존재한다. 따라서 일부 과거 문서의 ‘BF16 소스가 없다’는 문구를 현재 상태로 사용해서는 안 된다. 파일이 존재한다고 고정밀 추론이 빠르거나 동시에 메모리에 적재 가능하다는 뜻은 아니다.
